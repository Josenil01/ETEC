Aula 13: Fundamentos de HTTP

Começa aqui um projeto que vamos construir ao longo de sete aulas: um sistema de login real. Antes de escrever qualquer linha de back-end, precisamos entender como o navegador conversa com um servidor — os métodos HTTP, a URL e o que viaja em cada pedido.

1. Cliente e Servidor Precisam Conversar

Nas aulas passadas dominámos o Navegador (Front-End). Mas o navegador é apenas a "vitrine". Para os dados serem guardados de verdade — como quando alguém cria uma conta ou faz login — precisamos de enviá-los para o Servidor Web (Back-End).

A linguagem que o Navegador (Cliente) e o Servidor usam para conversar chama-se HTTP (Hypertext Transfer Protocol). Sempre que se clica num link ou se submete um formulário — como o de login que vamos construir e evoluir até à Aula 19 — o navegador está a despachar um "envelope" com instruções precisas. Não entender essas regras pode expor dados sensíveis, como a senha de um utilizador.

2. Os Protocolos de Ligação

O Que É Um Pedido HTTP? (Anatomia)

Um pedido HTTP é apenas texto — o "envelope" que o navegador escreve e envia ao servidor pela rede. Não importa o método, ele tem sempre as mesmas quatro partes. Veja como ficaria o pedido de login do nosso projeto:

pedido-http-cru.txt
POST /api/login HTTP/1.1
Host: api.meuprojeto.com
Content-Type: application/json
Content-Length: 46

{"email":"ana@email.com","senha":"1234abcd"}
1

Linha de Pedido: MÉTODO + caminho + versão HTTP. Diz o que se quer fazer (GET, POST...) e em que endereço.

2

Cabeçalhos (Headers): metadados no formato Chave: Valor, um por linha. Dizem para quem é (Host) e que tipo de dado vem a seguir (Content-Type).

3

Linha em branco: uma linha vazia obrigatória que separa os cabeçalhos do corpo — marca o "fim do envelope".

4

Corpo (Body): os dados em si. Num GET normalmente não existe (os dados vão na URL); num POST é aqui que o e-mail e a senha viajam escondidos.

O navegador monta este "envelope" sozinho quando usamos fetch — mas por trás de qualquer requisição, é sempre isto que viaja pela rede.

A Forma de Envio (Métodos HTTP)
Método GET (Obter)

Como um postal. A informação vai escrita do lado de fora da carta (na URL). É usado para pedir dados (ex: pesquisar um produto). Nunca use para enviar a senha do login!

Método POST (Enviar)

Como uma encomenda selada. Os dados vão escondidos dentro do "Corpo" (Body) do pedido. É assim que o nosso formulário de login vai enviar o e-mail e a senha.

O Endereço (URL)
https://api.meuprojeto.com/login?email=ana@email.com&senha=1234abcd

Esta é uma URL com uma QueryString — e é exatamente o que não queremos para um login.

  • O ponto de interrogação (?) indica o início dos dados.
  • email=ana@email.com é um par Chave=Valor.
  • O símbolo & une vários parâmetros — e aqui a senha ficou visível para qualquer um que veja a URL, o histórico do navegador ou os logs do servidor.
A Resposta do Servidor (Status Codes & Headers)

O servidor sempre responde com um Status Code — um número que diz se o pedido deu certo:

  • 200 OK — deu tudo certo (ex: login aceite).
  • 201 Created — algo novo foi criado (comum ao registar um utilizador).
  • 404 Not Found — esse endereço não existe.
  • 500 Internal Server Error — o servidor quebrou.

Os Headers (cabeçalhos) são metadados enviados junto do pedido/resposta, fora do corpo:

  • Content-Type — diz que tipo de dado está a viajar (ex: application/json).
  • Vamos vê-los ao vivo na aba Network do DevTools no Passo 6.
Mito comum: POST não é "seguro" por natureza — ele só evita que os dados apareçam na URL. Quem garante sigilo de verdade é o HTTPS, não o método escolhido. Na Aula 16 vamos ver como validar isso no servidor.

2.1 O Caminho do Pedido de Login (Fluxograma)

O caminho GET (azul) deixa os dados expostos na URL; o caminho POST (índigo) os leva escondidos no corpo — mas ambos só chegam com sigilo real se a ligação for HTTPS.

Passo 4 Construindo a QueryString (GET)

No método GET, anexamos as variáveis diretamente na URL. Usamos o URLSearchParams para montar isso facilmente.

cliente.js (Parte 2)🔒 Só leitura
btnGet.addEventListener('click', () => {
    // Captura os valores
    const email = inputEmail.value;
    const senha = inputSenha.value;

    // URLSearchParams formata automaticamente: ?chave=valor&chave2=valor2
    const parametros = new URLSearchParams({
        email: email,
        senha: senha
    });

    // A URL final fica exposta!
    const urlFinal = `${URL_SERVIDOR}?${parametros.toString()}`;

    saida.innerHTML = `
        > [ALERTA DE SEGURANÇA]<br>
        > Efetuando pedido GET...<br>
        > URL Acedida: <span style="color: #ef4444">${urlFinal}</span><br><br>
        > Qualquer pessoa que veja essa URL consegue ler a senha!
    `;
});

Passo 5 Criando um Payload (POST)

No método POST, a URL fica "limpa". Os dados vão empacotados num objeto JSON dentro do corpo (Body) do pedido HTTP.

cliente.js (Parte 3)🔒 Só leitura
btnPost.addEventListener('click', () => {
    const email = inputEmail.value;
    const senha = inputSenha.value;

    // Preparamos os dados como um Objeto
    const corpoLogin = {
        email: email,
        senha: senha
    };

    // JSON.stringify() converte o Objeto em texto para viajar na rede
    const jsonString = JSON.stringify(corpoLogin);

    saida.innerHTML = `
        > [PAYLOAD OCULTO DA URL]<br>
        > Efetuando pedido POST...<br>
        > URL Acedida: <span style="color: #818cf8">${URL_SERVIDOR}</span><br>
        > Corpo do Pedido (Payload Oculto): <br>
        > <span style="color: #818cf8">${jsonString}</span><br><br>
        > Nota: isto não aparece na URL nem no histórico — mas sigilo de verdade só existe com HTTPS.
    `;
});

Passo 6 Enviando de Verdade (Fetch Real)

Até aqui só montámos a URL e o payload — nada saiu do navegador de verdade. Agora vamos trocar a URL fictícia por uma real (httpbin.org, um serviço público feito para testar pedidos HTTP) e usar fetch para enviar o pedido de verdade. Abra o DevTools → Network antes de clicar nos botões do formulário lá em cima e observe o pedido a acontecer ao vivo.

Nota: fazemos isto aqui porque o assunto desta aula é provar que o pedido HTTP sai mesmo do navegador. Nas próximas aulas ainda não teremos um servidor.js realmente ligado, então vamos simular a resposta do servidor com uma Promise — mas a estrutura do código (loading, desativar o botão, bloco de código do lado do servidor bem marcado) é a mesma que vocês vão reconhecer a partir da Aula 14.

cliente.js (Parte 4)🔒 Só leitura
// Troca: em vez da URL fictícia, usamos um servidor real de testes
const URL_SERVIDOR = 'https://httpbin.org';

btnGet.addEventListener('click', async () => {
    const parametros = new URLSearchParams({ email: inputEmail.value, senha: inputSenha.value });
    const urlFinal = `${URL_SERVIDOR}/get?${parametros}`;

    // Isto é um pedido de rede DE VERDADE — aparece na aba Network
    const resposta = await fetch(urlFinal);
    const dados = await resposta.json();

    // httpbin devolve, entre outras coisas, os args que recebeu — prova de que chegaram!
    console.log(resposta.status, dados.args);
});

4. Exercícios

Nível: Fácil

01

Montador de Query String: Crie um objeto em JS chamado credenciais com as propriedades { email: "ana@email.com", senha: "1234abcd" }. Use a ferramenta new URLSearchParams(credenciais).toString() e faça um console.log() do resultado. Reparem que a senha fica perfeitamente legível ali — é exatamente o problema que o método GET causaria no nosso login.

Nível: Médio

02

A Magia do FormData: Em formulários maiores, capturar o .value campo a campo é cansativo. No HTML do Passo 1, adicione o atributo name="email" ao primeiro input. No handler de clique do POST, crie const form = document.getElementById('login-form'); e depois const dados = new FormData(form);. Imprima dados.get('email') na consola. O FormData captura automaticamente todos os inputs que tenham um atributo name!

Nível: Desafio

03

O Envio Real (Fetch com POST):

No Passo 6 vocês já viram um POST real chegar ao httpbin.org, que só devolve eco do que recebeu. Agora vamos usar a API pública JSONPlaceholder, que simula um servidor de verdade: ela cria o recurso e devolve um ID novo gerado no servidor — imaginem que é o registo de um novo utilizador no nosso sistema.
1. Crie uma função async para o clique.
2. Crie um objeto const novoUsuario = { title: email, body: 'Cadastro realizado', userId: 1 };
3. Dispare o fetch assim:
const resposta = await fetch('https://jsonplaceholder.typicode.com/posts', {
method: 'POST',
body: JSON.stringify(novoUsuario),
headers: { 'Content-type': 'application/json; charset=UTF-8' }
});
4. Converta a resposta para json (await resposta.json()) e exiba no login-output. Vai notar que a API devolve o objeto criado com um novo ID gerado no servidor!

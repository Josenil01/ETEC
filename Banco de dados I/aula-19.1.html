Servidores, APIs e Node.js

Antes de rodar o nosso script de conexão com o Neon, precisamos entender duas peças-chave: o que é um servidor e o que é uma API.

# O que é um servidor?

Servidor é um programa que fica ligado, esperando pedidos, e responde a eles. Não é necessariamente uma "máquina especial" — é só um software rodando em algum computador (que pode ser o seu notebook, um data center da Amazon, ou o data center do Neon) que fica "escutando" numa porta de rede, pronto para atender quem pedir alguma coisa.

Quem faz o pedido chama-se cliente. O navegador que você usa para abrir um site é um cliente. O celular do aluno é um cliente. O nosso script Node.js, quando conversa com o Neon, também age como cliente.

Cliente
(navegador, script Node)
— pedido (request) →
← resposta (response) —
Servidor
(programa sempre ligado)

Analogia: pense num restaurante. A cozinha é o servidor: fica sempre pronta, recebendo pedidos e devolvendo pratos prontos. Você (cliente) nunca entra na cozinha — só manda o pedido e recebe o resultado.

Exemplos de servidor no nosso curso:

  • O Neon mantém um servidor de banco de dados PostgreSQL sempre ligado, esperando comandos SQL.
  • Um site como nodejs.org tem um servidor web que responde com páginas HTML.
  • Quando escrevemos o nosso próprio backend em Node.js, ele também pode virar um servidor (isso vai aparecer nas próximas aulas).

# O que é uma API?

API significa Application Programming Interface (Interface de Programação de Aplicações). É o "cardápio" de coisas que um servidor aceita fazer — uma lista combinada de pedidos que ele entende, e o formato exato da resposta que ele devolve.

Seguindo a analogia do restaurante: a API é o cardápio que o garçom (a rede) leva até você. Você não precisa saber como o chef prepara o prato lá dentro — só precisa saber o nome do prato (o "endpoint") e como pedir (o formato do pedido). A cozinha (o servidor) devolve o prato pronto (a resposta) sempre no mesmo formato combinado.

No mundo da web, a maioria das APIs segue um padrão chamado REST: você manda uma requisição HTTP (o mesmo protocolo que o navegador usa para abrir páginas) para um endereço (endpoint), usando um método que diz a intenção — GET para buscar, POST para criar/enviar — e recebe a resposta normalmente em JSON, um formato de texto fácil de ler tanto por humanos quanto por programas.

Isso é exatamente o que o nosso script faz ao falar com o Neon:

// endpoint = o "prato do cardápio" que estamos pedindo
POST https://ep-old-paper-xxxx.neon.tech/sql

// corpo do pedido (o que queremos)
{ "query": "INSERT INTO categoria (...) VALUES ($1)", "params": [...] }

// resposta do servidor (JSON)
{ "rows": [ { "id_categoria": 1, "descricao": "Eletronicos" } ] }

Ou seja: a API é o contrato de comunicação; o servidor é quem cumpre esse contrato. O Neon expõe uma API HTTP para o seu banco de dados — por isso conseguimos mandar SQL usando fetch, em vez de precisar de um driver de banco de dados tradicional.

# O problema que encontramos

O arquivo script_db_quatum.js fazia esse pedido à API do Neon diretamente do navegador, carregado por uma tag <script> nesta página. Isso gera dois problemas sérios:

  1. CORS: o navegador bloqueia essa requisição porque a página (seu domínio local) e o servidor do Neon (*.neon.tech) são origens diferentes.
  2. Credencial exposta: a DATABASE_URL tem usuário e senha do banco escritos direto no código. No navegador, qualquer aluno abre o DevTools (F12) e vê tudo.

A solução para os dois problemas ao mesmo tempo é tirar esse código do navegador (cliente) e rodá-lo como um programa Node.js, que fala com a API do Neon servidor-a-servidor.

# O que é o Node.js?

Node.js é um ambiente de execução (runtime) de JavaScript fora do navegador. Ele usa a mesma engine que roda o JS no Google Chrome (a V8), mas removeu tudo que é específico de navegador (window, document, DOM) e adicionou acesso ao sistema operacional: ler/escrever arquivos, abrir conexões de rede, ler variáveis de ambiente, etc.

Na prática: o mesmo JavaScript que você já sabe (variáveis, funções, async/await, fetch) passa a rodar no terminal, como se fosse um programa comum — igual Python ou Java. É essa capacidade que nos permite escrever, no futuro, o nosso próprio servidor com Node.js.

JavaScript no navegador

  • Roda dentro de uma aba, sujeito a CORS
  • Tem acesso ao window, document, DOM
  • Código visível/baixável por qualquer visitante
  • Não acessa o sistema de arquivos

JavaScript com Node.js

  • Roda no terminal/servidor, CORS não se aplica
  • Tem acesso a process, fs, variáveis de ambiente
  • Código fica só na sua máquina/servidor
  • Lê e escreve arquivos, conecta em bancos de dados

# Passo a passo: preparando este projeto

1

Instalar o Node.js

Baixe a versão LTS em nodejs.org e instale. Depois, confirme no terminal:

$ node -v
v24.14.1
$ npm -v
11.7.0
2

Iniciar o projeto (criar o package.json)

Dentro da pasta Aula 19, o comando abaixo cria o package.json: o "documento de identidade" do projeto, que lista suas dependências e comandos.

# -y aceita as opções padrão sem perguntar nada
$ npm init -y
3

Instalar o pacote dotenv

O dotenv lê um arquivo .env e transforma cada linha numa variável de ambiente dentro do Node. É assim que tiramos a senha do banco de dentro do código.

$ npm install dotenv
4

Criar o arquivo .env

Crie um arquivo chamado .env (sem nome, só a extensão) na raiz da pasta, com a sua connection string do Neon:

DATABASE_URL=postgresql://usuario:senha@host/neondb?sslmode=require

⚠️ O .env nunca deve ir para o Git. Ele já está listado no .gitignore desta pasta, junto com node_modules/. Use o .env.example como modelo para quem clonar o projeto.

5

Rodar o script com Node

Nada de abrir o navegador. O script agora roda direto no terminal, falando com a API do Neon como cliente:

$ npm start
# ou, diretamente:
$ node script_db_quatum.js

# Um exemplo mínimo, antes do banco de dados

Para sentir a diferença, crie um arquivo ola.js com uma linha:

// ola.js
console.log("Olá do Node!");
console.log("Argumentos recebidos:", process.argv.slice(2));

E rode:

$ node ola.js Zé
Olá do Node!
Argumentos recebidos: [ 'Zé' ]

process é um objeto que só existe no Node — ele representa o próprio programa rodando no seu computador. É a prova de que este não é mais o JavaScript "de site": é JavaScript rodando como um programa de terminal, o mesmo tipo de programa que, mais para frente, vai virar um servidor.

# O que mudou em script_db_quatum.js

  • require('dotenv').config() carrega o .env antes de qualquer outra coisa.
  • const DATABASE_URL = process.env.DATABASE_URL substitui a senha escrita direto no código.
  • O fetch continua exatamente igual — desde a versão 18, o Node já traz o fetch nativo, sem precisar instalar nada extra para isso. É esse fetch que fala com a API do Neon.
  • Esta página HTML deixou de carregar o script via <script>: ele roda pelo terminal com npm start, não mais pelo navegador.

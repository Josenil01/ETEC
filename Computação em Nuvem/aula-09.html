Catálogo e Organização de Recursos

Hoje é a nossa primeira aula com laboratório de verdade: o professor demonstra ao vivo como criar e organizar recursos reais na Azure, enquanto você acompanha e pratica os conceitos.

Objetivo da Aula

Ao final desta aula, você será capaz de:

  • Descrever a hierarquia Grupo de Gerenciamento → Assinatura → Grupo de Recursos → Recurso.
  • Usar tags para organizar recursos por significado.
  • Explicar a consequência de apagar um grupo de recursos.
  • Comparar a estrutura de organização entre os três provedores.

1. Conceito

O catálogo de serviços é a lista completa do que dá para criar na nuvem — no portal Azure, é o "Todos os serviços" (All services) e o Marketplace, organizados por categoria (Computação, Armazenamento, Bancos de Dados, Redes, IA...). Já vimos como encontrar um item nesse catálogo (busca global, Aula 8) — hoje vemos como organizar o que você cria a partir dele.

A Hierarquia de Organização da Azure
Grupo de Gerenciamento (Management Group)
Assinatura (Subscription)
Grupo de Recursos (Resource Group)
Recursos (VM, banco, storage...)
  • Assinatura: fronteira de cobrança e de acesso — cada assinatura gera sua própria fatura.
  • Grupo de recursos: uma "pasta" lógica que agrupa recursos relacionados de um mesmo projeto (ex: a VM, o banco de dados e o storage de um único site). Apagar o grupo de recursos apaga tudo dentro dele de uma vez — poderoso e perigoso.
  • Grupo de gerenciamento: agrupa várias assinaturas (usado em empresas grandes, com departamentos diferentes).
Tags (Etiquetas)

Enquanto o grupo de recursos organiza pela estrutura, as tags organizam por significado — pares chave:valor (ex: ambiente:producao, projeto:loja-virtual) que você aplica em qualquer recurso, mesmo em grupos diferentes. Você pode filtrar/buscar por tag no catálogo para achar "todos os recursos do projeto X", não importa onde estejam organizados.

2. Exemplo — A Estrutura da TechBox

A TechBox (Aula 2) organizou sua conta assim:

  • 1 assinatura de Produção e 1 assinatura de Desenvolvimento (separadas, para nunca misturar teste com o site real).
  • Dentro de Produção: grupo de recursos rg-loja-web (VM + App Service do site) e rg-loja-dados (banco de dados).
  • Toda a VM, banco e storage relacionados ao site levam a tag projeto:loja-virtual.

Por que separar em dois grupos de recursos (web e dados) em vez de um só? Porque times diferentes cuidam de cada parte, e times diferentes de acesso podem ser concedidos por grupo de recursos — o time de banco de dados não precisa ter permissão para mexer na VM do site.

Cuidado real: se alguém, sem querer, apagar o grupo rg-loja-dados, o banco de dados inteiro some junto — é por isso que a Aula 11 vai ensinar a colocar um "cadeado" (lock) em grupos de recursos importantes.

4. Cada Provedor Organiza Diferente

Essa é uma das maiores diferenças estruturais entre os três — não é só nome, a estrutura em si muda:

Conceito Azure AWS Google Cloud
Fronteira de cobrança/acesso Subscription Account Project
"Pasta" obrigatória para recursos Resource Group (sempre existe) Não existe por padrão — Resource Groups na AWS são só uma visão baseada em tags, opcional Não existe separado — os recursos já ficam direto dentro do Project
Etiquetas Tags Tags Labels
A Azure é a única com um "Grupo de Recursos" obrigatório como camada própria entre a assinatura e o recurso. No Google Cloud, o Project já faz esse papel sozinho (mistura conta de cobrança + agrupamento). Na AWS, quem organiza de verdade são as tags — "Resource Groups" existe, mas é opcional e só uma forma de visualizar recursos já marcados com tag.

Exercício 1 — Classifique o Nível

⭐

Cenário

Diga se cada item é uma assinatura, um grupo de recursos ou uma tag:

  1. rg-loja-dados
  2. ambiente:producao
  3. "Desenvolvimento" (a conta que recebe a fatura separada dos testes)
Dica

Releia o exemplo da TechBox.

Solução

  1. Grupo de recursos
  2. Tag
  3. Assinatura

Exercício 2 — Consequência de Apagar

⭐⭐

Cenário

Alguém, por engano, apaga o grupo de recursos rg-loja-dados da TechBox.

O que fazer

O que acontece com o banco de dados que estava lá dentro? E o site (que fica em rg-loja-web) também é afetado diretamente?

Dica

Releia o box vermelho "Cuidado real" da Seção 2.

Solução

O banco de dados é apagado junto — apagar um grupo de recursos apaga tudo dentro dele. O site em si (rg-loja-web) não é apagado diretamente, pois está em outro grupo, mas provavelmente vai parar de funcionar corretamente por depender do banco que não existe mais.

Exercício 3 — O Project do Google Cloud

⭐⭐

Cenário

Explique por que dizemos que o "Project" do Google Cloud "mistura" dois conceitos que na Azure são separados.

Dica

Releia a Seção 4 e o box amarelo.

Solução

Na Azure, "assinatura" (cobrança/acesso) e "grupo de recursos" (organização dos recursos) são dois níveis diferentes. No Google Cloud, o Project já cumpre os dois papéis ao mesmo tempo — é a fronteira de cobrança e onde os recursos ficam guardados diretamente, sem uma camada extra de agrupamento.

Exercício 4 — Complete a Hierarquia

⭐

Cenário

Ordene do maior para o menor: Recurso, Grupo de Recursos, Grupo de Gerenciamento, Assinatura.

Dica

Releia o diagrama da Seção 1.

Solução

Grupo de Gerenciamento → Assinatura → Grupo de Recursos → Recurso.

Exercício 5 — Parecer Técnico (Boss Final)

⭐⭐⭐⭐

Uma escola vai colocar 3 sistemas na nuvem: biblioteca, financeiro e matrícula online. Cada sistema tem sua VM e seu banco de dados próprios. O financeiro exige acesso mais restrito que os outros dois.

O que fazer

Proponha uma estrutura de grupos de recursos (nomes inclusos) para essa escola, e pelo menos 2 tags que ajudariam a encontrar rapidamente todos os recursos de um sistema específico, mesmo que estivessem espalhados em grupos diferentes.

Dica

O requisito de acesso mais restrito do financeiro é uma boa pista para separá-lo em seu próprio grupo de recursos.

Solução (exemplo de proposta)

Grupos de recursos: rg-biblioteca, rg-matricula, e rg-financeiro separado dos demais justamente pela exigência de acesso restrito (permissões diferentes por grupo, Aula 6). Tags sugeridas: sistema:biblioteca / sistema:matricula / sistema:financeiro (para achar tudo de um sistema mesmo se algum recurso estiver em outro grupo por engano) e criticidade:alta no financeiro, para sinalizar que precisa de atenção extra (ex: locks, Aula 11).

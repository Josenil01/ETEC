Criar e Acessar uma VM

Hoje o professor cria uma VM de verdade, ao vivo, na Azure — e você pratica o acesso a um terminal Linux de verdade no Killercoda, sua conta própria e gratuita.

Objetivo da Aula

Ao final desta aula, você será capaz de:

  • Identificar as 4 etapas do assistente de criação de uma VM (Basics, Disks, Networking, Management).
  • Diferenciar o acesso via RDP (Windows) do acesso via SSH (Linux).
  • Executar comandos básicos de terminal Linux num ambiente real.
  • Justificar o uso do auto-shutdown como prática de consumo consciente.

1. Conceito

O Assistente de Criação (4 abas)

1. Basics (Básico)

Grupo de recursos (Aula 9), nome da VM, região (Aula 6), imagem e tamanho (Aula 12), usuário/senha de administrador, e as regras de porta de entrada (Aula 14).

2. Disks (Discos)

Tipo de disco do sistema operacional (Standard, Premium SSD) e discos de dados adicionais, se precisar.

3. Networking (Rede)

Rede virtual, sub-rede, e se a VM recebe um IP público (Aula 14).

4. Management (Gerenciamento)

Auto-shutdown: desliga a VM automaticamente todo dia num horário — a ferramenta oficial da Azure para o hábito de consumo consciente (Aula 7)!

Acessar VM Windows

Via RDP (Remote Desktop Protocol, porta 3389) — a Azure gera um arquivo .rdp para baixar e abrir, que conecta numa área de trabalho remota completa.

Acessar VM Linux

Via SSH (Secure Shell, porta 22) — um terminal de linha de comando, geralmente autenticado por usuário/senha ou por chave criptográfica.

2. Exemplo — Criando a vm-loja-web

Acompanhe como a TechBox preencheria o assistente para colocar o site no ar:

  1. Basics: grupo de recursos rg-loja-web (Aula 9), nome vm-loja-web, região Brasil Sul (Aula 6), imagem Ubuntu Server, tamanho Standard_D2s_v5 (Aula 12).
  2. Portas de entrada: permite SSH (22) e HTTP (80) — só o necessário (Aula 14 explica por quê isso importa).
  3. Disks: disco padrão, suficiente para um servidor web simples.
  4. Networking: IP público habilitado, para o site ser acessível pela internet.
  5. Management: auto-shutdown configurado para desligar a VM às 23h — mesmo sendo uma VM de produção, isso evita esquecimentos em ambientes de teste que às vezes reaproveitam esse mesmo template.
  6. Review + Create → alguns minutos depois, a VM está pronta.
  7. Acesso: como é Linux, conecta via SSH usando o IP público gerado.

O que a turma acompanha:

Passo 2 — Sua vez: terminal Linux real no Killercoda

Depois de ver a VM sendo criada, é sua vez de praticar o que você faria depois de conectar via SSH: usar a linha de comando Linux.

Link do playground:

killercoda.com/playgrounds/scenario/ubuntu
  1. Faça login (conta escolar, GitHub, Google ou e-mail — sem cartão) e inicie o playground Ubuntu.
  2. Rode whoami e hostname — exatamente como faria numa VM recém-criada, para confirmar quem é você e onde está.
  3. Rode ls, pwd e cd /var/www (crie a pasta com mkdir -p /var/www se ela não existir) — simulando onde ficariam os arquivos de um site.
  4. Rode sudo apt update — o mesmo comando que você usaria numa VM real antes de instalar qualquer coisa.
A sessão do Killercoda expira em torno de 60 minutos — não tem problema, é só um ambiente de prática, sem custo e sem necessidade de "limpar" nada depois.

4. Como Se Conectar em Cada Provedor

Azure

Botão Connect no portal → baixa arquivo RDP (Windows) ou comando SSH pronto (Linux).

AWS

SSH com par de chaves (key pair) baixado na criação, ou EC2 Instance Connect (SSH pelo próprio navegador).

Google Cloud

Botão SSH direto no Console, que abre um terminal no navegador, sem configurar nada antes.

Exercício 1 — Em Qual Aba?

⭐

Cenário

Em qual das 4 abas do assistente (Seção 1) você configuraria: (1) o auto-shutdown; (2) se a VM tem IP público; (3) o tipo de disco?

Dica

Releia os 4 cards da Seção 1.

Solução

(1) Management. (2) Networking. (3) Disks.

Exercício 2 — RDP ou SSH?

⭐

Cenário

Diga qual protocolo (RDP ou SSH) e qual porta (3389 ou 22) se usa para acessar: (1) uma VM Windows; (2) uma VM Linux.

Dica

Releia os dois cards da Seção 1.

Solução

(1) RDP, porta 3389. (2) SSH, porta 22.

Exercício 3 — Por Que Auto-Shutdown?

⭐⭐

Cenário

Explique, conectando com outra aula deste curso, por que configurar o auto-shutdown numa VM de desenvolvimento é uma boa prática.

Dica

Pense no caso da "VM Esquecida".

Solução

É a versão automatizada do consumo consciente (Aula 7) — evita repetir o erro da "VM Esquecida", onde ninguém desligou a VM manualmente e ela ficou consumindo (e cobrando) à toa.

Exercício 4 — Qual Provedor, Qual Método?

⭐

Cenário

Um colega usa um "par de chaves" para conectar via SSH numa instância. Em qual provedor ele está?

Dica

Releia a Seção 4.

Solução

AWS.

Exercício 5 — Roteiro de Criação (Boss Final)

⭐⭐⭐⭐

Uma escola quer uma VM Linux para hospedar um pequeno sistema de biblioteca (acesso só de dentro da escola, sem necessidade de ficar ligada à noite).

O que fazer

Escreva um roteiro com o que preencher em cada uma das 4 abas do assistente para esse cenário específico, incluindo se deve ou não ter IP público e um horário sugerido de auto-shutdown.

Dica

"Acesso só de dentro da escola" é uma pista sobre IP público; "sem necessidade de ficar ligada à noite" é sobre auto-shutdown.

Solução (exemplo de roteiro)

Basics: grupo de recursos próprio (ex: rg-biblioteca), imagem Ubuntu Server, tamanho B-series (baixo uso). Disks: disco padrão. Networking: como o acesso é só de dentro da escola, não precisa de IP público — pode ficar só com IP privado, acessível pela rede interna. Management: auto-shutdown configurado para o fim do expediente (ex: 18h), já que ninguém precisa acessar à noite.
